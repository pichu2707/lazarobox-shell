## 2. What an orchestrator needs that does not exist

1. Key generalization: turns, hub sessions, waits and tagged events are all keyed by PaneId. Workers need `SessionKey`/`WorkerId` (RunId,WorkerId) with own socket+token+scope (approvals, audit, jail grants per worker) and their own workdir/origin.
2. RunManager (new; pure core state machine like settle.rs/mcp.rs + runtime shell): spawn, status, wait(ids,timeout), collect, cancel, kill-on-quit (reuse `Chats::shutdown`), per-worker deadline, max parallel (CLI workers are node processes and share one subscription rate limit; default 1-2), run budget (workers, turns, wall clock, cost). States: Queued/Running/WaitingApproval/Done/Failed/Cancelled/TimedOut/Refused.
3. The 15-min trap: a blocking spawn+wait MCP call is capped by MCP timeout 900 s AND by the orchestrator turn's 15-min total. Long runs need async spawn, bounded wait (<=120 s per call) and collect, with orchestrator turns resumable (one-shot stateless processes) from a run ledger that lazarobox owns. The orchestrator context carries a compact ledger (worker id, kind, status, summary), not worker transcripts.
4. Approvals: one pending approval per chat today. N workers asking at once need a FIFO queue labeled "worker 2/3 code claude>sonnet", no auto-approve for workers by default, a timer never approves (existing invariant), cancelling a worker denies its pending asks.
5. Worker tool surface by kind: Review/Summarize read-only (find_dir,list_dir,read_file); Code needs write tools (write-tools change, unbuilt) and a captured test runner (new non-pane `run_command` tool with timeout/limits; not designed anywhere) to do TDD. Workers MUST NOT get spawn_agent (no recursion); only the orchestrator gets orchestration tools, only when enabled.
6. Results/diffs: worker result = final text wrapped untrusted (D14 nonce) + structured status; with write tools a per-worker change ledger (paths, sizes, diff hash) so collect returns "files changed" and the user can review/revert. No git integration exists; per-run git worktree is a later option.
7. Fail-closed jail per worker: reuse `availability_with` per resolved engine at SPAWN time (NoJail, Outdated, ModelMissing, Unsupported); spawn returns a structured refusal and never falls back to another engine (current rule engine.rs:255). `availability_with` is hard-wired to Task::Chat (engine.rs:281) and must be parametrized by Task. The orchestrator must be told which kinds are unavailable.
8. TUI: `Entry::Worker` rows (like `Entry::Tool`) in the transcript (kind, engine>model, status, elapsed); full-pane run view to read a worker transcript (precedents `list_open`, `memory_view_open`, `tag_editor_open`, app/run.rs:91); key to cancel one/all; ORCH badge like AUTO/RUN; the approval overlay shows the worker label. Worker transcripts are not stored in chat history (summary only).
9. Persistence: v1 in-memory ledger + final summary as a normal assistant message; later a runs table in chat_store (SQLite) and engram notes for run summaries (not worker chatter).
10. Config: `[ai.orchestrator] enabled=false, max_parallel, max_workers_per_run, budget`; which Task the orchestrator itself uses (open question); worker kind -> `cfg.resolve(Task::X)` at spawn.
11. Cost: every CLI worker call is spend against the user's plan or API key; per-call context is re-sent (provider-side prompt caching only). Show per-worker/per-run estimate once Usage events exist; a budget cap must fail closed.

## 4. Approaches (H1 build)

- **A. Sync `delegate` tool**: orchestrator = Chat-pane turn with extra MCP tool `delegate{kind,prompt}` blocking until the worker ends; worker = nested Runner turn in ToolHost. + smallest (~1 PR), easy to test. - blocked by the 900 s/15-min caps, parallel only if the CLI batches calls, poor cancel, approval collision, no run state.
- **B. lazarobox-driven scheduler**: orchestrator LLM returns a structured plan (json-schema); RunManager executes a DAG and re-calls the orchestrator with results. + deterministic, budget/cost control, no timeout trap, very testable. - not the decided model (agent calls spawn/wait/collect), less autonomy, plan schema differs across 3 CLIs, drifts toward H2.
- **C. (RECOMMENDED) Async tools over a RunManager**: `spawn_agent{kind,prompt}` -> id; `wait{ids,timeout<=120s}`; `collect{id}` (untrusted-wrapped); `cancel{id}`; a RunManager in runtime owns worker tasks independent of the orchestrator turn; workers are a new `WorkerSession` keyed by (RunId,WorkerId) reusing `runner_with`/`run_turn`/Hub/Waits after generalizing PaneId -> SessionKey; orchestrator turns resumable via a ledger. Pure core `core/ai/orchestra/{run,worker,ledger}.rs`, runtime shell `runtime/orchestra.rs`, app: approval queue, Entry::Worker, run view. + matches decision, survives caps, parallel-ready, testable with fake `Runner` and tokio paused time. - SessionKey refactor (chat.rs, session.rs, approver.rs, app events), approval queue, ledger prompts.

Worker abstraction: child chat sessions on fake PaneIds (pollutes layout/Effect/Tagged, id collisions) vs new WorkerSession with contract `WorkerSpec{kind, engine, model, prompt, toolset, budget} -> WorkerResult{status, text, usage, files_changed, refusal}` (recommended). Collect: async spawn + bounded wait (recommended) vs fully sync.

## 5. First slice (smallest vertical proof of the worker contract)

- IN: `[ai.orchestrator] enabled` (default off) + toggle/badge following the AUTO/RUN pattern; tools spawn_agent{kind:general|code|review|summarize, prompt}, wait, collect, cancel offered ONLY to the orchestrator session; ONE worker at a time; worker engine/model from `cfg.resolve(Task::X)`; availability/jail checked at spawn with a structured refusal; worker prompt = builtin `<profile>/<task>.md`; worker tools = READ-ONLY subset through the existing ToolHost (no run_in_pane, no spawn_agent); result = final text capped 32 KiB + status + elapsed, untrusted-wrapped; worker deadline (10 min default); Ctrl+C cancels worker and orchestrator; Entry::Worker row; read_file approvals reuse the overlay labelled with the worker (one worker => no queue); whole contract tested with a fake Runner; README section incl. provider-terms note.
- OUT: file writes, TDD/SDD semantics, running tests, parallel workers + approval queue, full SessionKey refactor (thin WorkerId wrapper ok), persistence/resume across restart, cost numbers, run view pane, nested orchestrators, special Review/Summarize behaviours beyond prompt choice, OpenAI-compat adapter, API-key mode, git worktrees.
- Suggested sequence: S1 contract + one read-only worker; S2 Usage events + cost row; S3 approval queue + parallel(2); S4 write-tools for Code workers + change ledger; S5 run_command/test tool (TDD loop); S6 SDD/TDD playbooks + ledger phases; S7 run view + persistence.

## 6. Risks and open questions

Risks: provider ToS (above), incl. consumer-plan account action; the vision "writes code" needs write-tools + a test-runner tool that do not exist (large, security-heavy, separate SDDs); 900 s/15-min caps; single-slot approvals; PaneId keying refactor blast radius (app.rs ~8k lines with tests); prompt injection via worker output into the orchestrator (D14 wrapper, orchestrator cannot approve); 429/rate limits when parallel on one subscription; cost blow-up; small Ollama models cannot orchestrate (gate the orchestrator role to claude/codex/gemini or document); gemini being replaced by Antigravity CLI (id churn); codex/gemini refused without jail, claude unjailed on macOS (workers inherit per engine); profile is global not per task; only Ollama is a local engine (OpenAI-compat unbuilt); jail denies workers network/exec so TDD needs a lazarobox-side executor.

Open questions (answered in the proposal question rounds, engram `sdd/agent-orchestrator/proposal-questions`): 1 Which Task/engine runs the orchestrator itself? 2 Who approves worker tool calls? 3 Max parallel workers, max workers per run, wall-clock and cost budget; behaviour at budget? 4 Can workers write files, and where? 5 What do Review and Summarize workers return? 6 How are TDD/SDD expressed? Who runs the tests? 7 Live worker transcripts or summaries only? 8 Runs persisted/resumable after restart, recorded in engram? 9 Consumer logins vs API keys? 10 Unavailable worker engine: fail the spawn or let the orchestrator reassign? 11 May the orchestrator use run_in_pane? 12 Cost visibility acceptable only where the CLI reports it?

## Recommendation

Approach C with slice S1, after a proposal question round on items 1, 2, 4, 6, 9. Do not start the writes/TDD vision before write-tools and a run_command tool have their own SDDs. Provider-terms posture is a product decision for the user.
